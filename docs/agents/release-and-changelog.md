# Release and changelog

Read this before touching the release workflow, `lerna.json`, the root `version` script or `scripts/generate-changelog.mjs`. Paths are relative to the repository root.

## Release

Release: the `Release to npm` workflow (`.github/workflows/release.yml`, manual dispatch — pick the bump and dist-tag, or tick `dry_run`). It runs the CI gates, then `lerna publish <bump> --no-private --exact --yes --force-publish`, then `gh release create` on the tag lerna pushed. For a `latest` release it also lists the new `@c2n/mcp` version in the MCP Registry as `io.github.code2nguyen/c2n` (`packages/tools/mcp/server.json`, whose versions the root `version` script stamps; `mcp-publisher login github-oidc`, best effort, skipped when that version is already listed). The registry verifies the npm package through its `mcpName` field, so keep it equal to the `server.json` name. `NPM_TOKEN` (an npm **automation** token) is an environment secret on the `release` environment, which the job declares. Locally the equivalent is `npm run build && npm run build:tools` then that same `lerna publish`.

`lerna version` writes the new version into `lerna.json` and every publishable `package.json`, runs the lifecycle scripts, then stages and commits. The **root** `version` script stamps the build-only MCP registry before `build-skill.ts` regenerates and stages the versioned skill catalog and plugin manifests. The registry itself remains ignored and is rebuilt by CI and package prepack. `--force-publish` is there because fixed-mode `lerna version` otherwise exits with "No changed packages to version" when a dispatch's only changes are in tooling.

## Changelog

Changelog: `scripts/generate-changelog.mjs` (`npm run changelog`, unit-tested by `scripts/generate-changelog.test.mjs`) builds `CHANGELOG.md` and `apps/ui/src/data/changelog.json` from the commit history, both committed and prettier-formatted on write. Releases are delimited by the `chore(release): publish v<version>` commits, not tags (tags may point off the branch); conventional `feat`/`fix`/`perf` commits and breaking changes are kept, housekeeping types (`chore`, `ci`, `test`, `docs`, `refactor`, …) and `ci`/`release` scopes are dropped, `ui`/`examples`/`gallery` scopes go to a "Docs site & examples" section, and free-form sentence subjects are classified by their first word. It needs full history (it refuses a shallow clone) and writes released history only, so it is stable between releases: the release workflow runs `npm run changelog -- --next <version>` right after `lerna version`, and the GitHub release body is that version's `CHANGELOG.md` section followed by GitHub's generated PR list. The docs site renders the JSON at `/changelog` (`apps/ui/src/pages/changelog.astro`, linked from the header version badge and the footer) as a short `c2-timeline` of the 10 latest releases: package changes only, three lines per section, the rest behind a `c2-details`, and a component a release introduces (a `feat` line "Add c2-<id> …" / "Add @c2n/<id> …" scoped to a documented id) shown as a live preview card from `component-previews.ts` (up to four per release; `component-modules.ts` loads when the first card nears the viewport). The preview helper classes live in `src/assets/component-previews.scss`, shared with the landing gallery. Write commit subjects as Conventional Commits with the package as scope (`feat(table): …`) — that subject is the changelog line.
