# Adding a component

Read this when scaffolding a component (with the `new-component` skill) or making one reachable by agents. Not loaded automatically: open it when the task matches (the root `CLAUDE.md` and `packages/components/CLAUDE.md` point here). Paths are relative to the repository root.

## Scaffolding

`npm run generate` prompts for a name and then: scaffolds the package into `packages/components/<name>` from `scripts/generator/files/wc`, scaffolds its Playwright suite from `scripts/generator/files/wc-test` into `<package>/test/`, adds a doc stub under `apps/ui/src/content/components/`, adds the build target to the root `package.json` and to `packages/tools/theme/package.json`, and wires up everything the UI app needs: the manifest import and `normalizedManifests` entry in `apps/ui/src/store/component-manifests.ts`, the `@c2n/<name>` dependency in `apps/ui/package.json` and in the umbrella's `devDependencies`, the side-effect import in `component-modules.ts`, a placeholder in `component-previews.ts`, and a gallery stub under `apps/ui/src/content/gallery/`. **Run `npm install` afterwards** — it creates the `node_modules/@c2n/<name>` workspace symlink, without which `npm run ui:build` fails to resolve the new manifest. The stubs are placeholders: fill in the doc page (including its `intents:` frontmatter), the gallery cards, the preview markup and the test suite, or delete the gallery file if the component has no variants worth showing. A new component is also scored for AI readiness (`npm run mcp:readiness`, which reports it as new): grade A, its discovery requirements added to `packages/tools/mcp/scripts/readiness/tasks.json` and ranking it in the top 3, and `packages/tools/mcp/readiness/` committed with it (the `new-component` and `ai-readiness` skills have the steps). Every one of those registry entries goes in at its alphabetical place through the generator's `register` action (`scripts/generator/sorted-lists.ts`), never at the top of its list: two component PRs open at once then touch different lines and merge without a conflict. Keep those lists sorted when editing them by hand (`node scripts/generator/sorted-lists.ts` re-sorts them all). If a merge of two component PRs still conflicts, it is in generated output (`packages/umbrella/package.json` and `src/*`, the skill catalog, `package-lock.json`): take either side, then rerun `npm install && npm run build:tools && npm install` and commit what they write (the second install records any dependency `build:tools` wrote into the umbrella's `package.json`; `npm ci` rejects a lockfile that disagrees with it).

## Reachable through MCP and llms.txt

**Every component is reachable by a coding agent through the `@c2n/mcp` server and the docs site's `/llms.txt`.** A component an agent cannot find is one it hand-rolls instead, so a component is not done until both list it. Both are generated, never hand-edited: the MCP registry from the package's `custom-elements.json` and its docs page (`packages/tools/mcp/scripts/build-registry.ts`), `/llms.txt` from the docs collections (`apps/ui/src/pages/llms.txt.ts`). Reachability therefore comes from the inputs:

- **A docs page** in `apps/ui/src/content/components/` (icon sets: `content/icons/`), with `package`/`tag` set when its id is not the npm name / element tag. Without it the component is missing from `/llms.txt` and the registry marks it `undocumented`. A package documented on several pages (`@c2n/chart`) needs a page per element an agent should find, each with its `apiTags`.
- **Discovery frontmatter** on that page: a `description` and 3–5 `intents` (requirements worded the way a developer asks, without naming the component), plus `keywords` when the widget goes by other names. The generator's `TODO:` placeholder intents are dropped from the registry, so they count as missing. This is what `search_components` ranks on and what `/llms.txt` prints.
- **A built manifest** that documents the public API (rule 1 in `docs/agents/component-foundation.md`, and "The manifest pipeline" in `packages/components/CLAUDE.md`): every element, attribute, slot, event, CSS variable and part an agent may use has its JSDoc tag, since `get_component` and `validate_markup` know nothing the manifest omits. Every element of the package is reachable by its tag, children included (`c2-table-column`), not only the page's main element.
- **An entry in `@c2n/components`** (`packages/umbrella`), so the install and import lines both sources print are the ones that work.

Two generated files also take the new component, and CI regenerates and diffs both: `node scripts/generate-slot-styling-audit.mjs` adds its slots to `scripts/data/slot-styling-audit.json` (each new entry then needs its decision, which `npm run docs:check` checks; run the generator again after writing them, since it decides the file's layout and CI compares against it), and `node lab/scripts/gaps.mjs` adds it to `lab/GAPS.md` (after `build:tools`, which writes the registry it reads). Commit both.

Check it before calling a component done: `npm run check:reachability` (after `npm run build:registry -w packages/tools/mcp`; a gate in `component-tests.yml` and `deploy.yml`) fails on a component with no served docs page, no description, fewer than three intents, no `@c2n/components` entry or a tag that does not resolve, and `npm run mcp:readiness` grades it A with its discovery requirements in `packages/tools/mcp/scripts/readiness/tasks.json` ranking it in the top 3. A change that renames a tag, moves a page or splits a package keeps both sources pointing at it.
