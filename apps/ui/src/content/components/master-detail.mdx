`c2-master-detail` lays out a list and the record it opens: an inbox and the open message, orders and the order, files and the preview. The layout follows the element's **own width**, not the window's, so it is right inside a dialog, a split panel or a narrow column. From `breakpoint` (720px) up it is a **split**: the `master` slot in a column beside the `detail` slot, with the `placeholder` slot in the detail pane while nothing is open. Below it, `collapse="stack"` (the default) shows one pane at a time: opening slides the detail over the list and moves focus into it, and the built-in Back bar returns to the list and to the row the user came from. `collapse="overlay"` instead slides the detail over the list, which stays visible behind a backdrop; Back, Escape or a click on the backdrop closes it. The element owns no selection: listen to your list, fill the `detail` slot and set `open`. Every user close fires a cancelable `close-request` first (cancel it to keep unsaved changes), and the layout in use is the `layout` property, the `layout-change` event and the `:state(split)` / `:state(stack)` / `:state(overlay)` custom states. Any element with a `master-detail-back` attribute inside the detail works as a Back button. Give the host a height (each pane scrolls on its own) and, in a flex or other shrink-to-fit parent, a width: it sizes from its container, not from its content.

The app decides what "open" means: fill the `detail` slot from the selected row, then set `open`. In the split layout the selection stays visible and focus stays in the list, so the arrow keys and Enter walk through records; in the other two, Back clears `open` and puts focus back on the row.

```typescript tag=CodeBlock
const layout = document.querySelector('c2-master-detail')
list.addEventListener('selection-change', (event) => {
  showRecord(event.detail.value[0])
  layout.open = true
})
layout.addEventListener('close-request', (event) => {
  if (form.dirty && !confirm('Discard your changes?')) event.preventDefault()
})
```
