# Component foundation

Read this before designing a component or adding a feature to one: the six rules decide the public API. Not loaded automatically: open it when the task matches (the root `CLAUDE.md` and `packages/components/CLAUDE.md` point here). Paths are relative to the repository root.

Six rules hold for every component, new or updated. They decide the shape of the public API before any code is written, and a change that adds a feature applies them to that feature.

| Concern      | Mechanism                                                                 | Not                                                    |
| ------------ | ------------------------------------------------------------------------- | ------------------------------------------------------ |
| Presentation | `--c2-*` CSS variables                                                    | a `size`/`color`/`variant` attribute for a look        |
| Extension    | named slots (wrapper exported as a `part`), then `render<Part>` functions | a flag or enum per content variation, a forked copy    |
| Data         | declarative markup **and** an in-memory property, plus a `dataSource`     | a property-only API, or a fetch built into the element |
| Actions      | an action zone: a named slot the app fills, plus methods and events       | a built-in button, flag and event per command          |
| Text         | message tokens in `src/messages.ts`, translated by the app                | a string literal in the template                       |
| Proof        | a live card in the component's gallery (`apps/ui/src/content/gallery/`)   | a feature that exists only in the API table            |

1. **Presentation is customizable through CSS variables.** Everything a designer may want to change (size, spacing, colour, typography, border, radius, shadow, motion) is a documented `--c2-<name>__<part>[__<state>]--<property>` variable with its default in the `$theme` map. "Theming convention" in `packages/components/CLAUDE.md` has the grammar and the attribute/variable split.

2. **Content is extensible through slots, then renderer functions.** Never grow an attribute per content variation.
   - **A slot** for a region the author writes once in markup: icons, a toolbar, a footer, the `empty`/`loading`/`error` states. Give it a built-in default, hide the region when the slot is empty, and document it with `@slot`.
   - **The element that wraps a slot exports a CSS part.** A slot has no box of its own, so the wrapper is the only place a consumer can style the region: its layout, padding, a border, a sticky position. Give it a `part` named after the slot (`<div class="footer" part="footer"><slot name="footer"></slot></div>`), the default slot's wrapper a part named for its role (`content`, `items`), and document each with `@csspart`. Variables remain the first choice for everything the component foresaw; the part is the hook for what it did not. A renderer's output sits in the shadow root too, so it may carry its own `part` (`` html`<span part="badge">…</span>` ``) for the page to style. A part name is public API: renaming one is a breaking change.
   - **A renderer function** for content repeated per item of data, which a slot cannot express: `@property({ attribute: false }) render<Part>?: <Class><Part>Renderer`, named `renderItem`, `renderCell`, `renderLabel`… The type is exported next to the class as `(context: <Class><Part>Context) => unknown` (anything Lit can render: a `TemplateResult`, a string, a node). It takes **one context object** (`{ item, index, … }`), so a field can be added later without breaking callers. With no renderer set, the built-in rendering is the default.
   - The component keeps what makes the item work: its container element, role and ARIA state, keyboard handling, selection, virtualization. The renderer supplies the content only (`c2-autocomplete` still creates each `c2-list-item`; `renderItem` fills it).
   - When a component has several replaceable parts, offer the narrow renderers beside the whole-item one (`c2-tree`: `renderItem`, `renderLabel`, `renderIcon`, `renderActions`), so the common case does not rebuild the whole row.
   - Reference: `c2-virtual-list` (`renderItem`), `c2-table-column` (`renderCell`, `renderHeader`), `c2-tree`, `c2-steps`.

3. **A component that displays a collection takes its data three ways**, all feeding one internal model:
   - **Declarative**: child elements (`c2-table-column`, `c2-tree-item`, `c2-step`, `c2-list-item`) and/or a JSON attribute through `jsonPropertyConverter` (`rows`, `items`, `data`). This is the form that works in plain HTML, in a server render and in an MDX fence, so it must cover the common case on its own.
   - **In memory**: the same array assigned to the property.
   - **Data source**, for data that is large, remote or paged: `@property({ attribute: false }) dataSource?: <Class>DataSource`, an exported interface with one async method (`getRows(request)`, `getItems(request)`). The request carries the window (`start`, `count`) and whatever the component delegates to the source (`sort`, `search`); the result carries the items and the `total`. The component never fetches by itself and knows no URL.
   - With a `dataSource`, the component owns the loading, empty and error states (each replaceable through its slot), drops a response a newer request has superseded, and warns once in the console about a feature it cannot honour without the whole dataset (`c2-table` ignores `group-by`).
   - When two forms are given at once, one wins, and the property's JSDoc says which (`c2-table`: column children win over `columns`; `dataSource` is used instead of `rows`).
   - Reference: `c2-table` (`rows`, `columns` or `c2-table-column`, `dataSource`), `c2-virtual-list`, `c2-tree` (`items` or `c2-tree-item`, `loadChildren`), the charts (`data`, `c2-chart-series`, `dataSource`).

4. **Every feature is demoable in the gallery of the Astro app.** A feature is done when a reader can see it work at `/components/<id>/gallery`: each variable group worth restyling, each slot, each renderer, each data form has a card (the Docs usage card covers only the overview).
   - A feature reachable from markup (attributes, slots, CSS variables, declarative data) is a plain ` ```html tag=MdxCodeBlock,label=… ` fence.
   - A property-only feature (a renderer, a `dataSource`) cannot be written in a fence. Mark the element in the fence with `data-<name>-example="<case>"`, assign the property from `apps/ui/src/components/<Name>ExamplesRuntime.astro` (a `<script>` that finds those elements; `AutocompleteExamplesRuntime.astro` and `KanbanExamplesRuntime.astro` are the pattern), render that component once in the gallery MDX, and show the code a consumer writes in a ` ```ts tag=CodeBlock ` fence under the grid.
   - A `dataSource` card uses an in-page source that resolves after a short delay, never the network, and shows the loading state and at least one further page.
   - Adding a feature to an existing component adds its card in the same change. If a feature cannot be shown in a card, say why in the pull request.

5. **A complex component offers action zones instead of building the actions in.** When a component has room for commands (a toolbar, a header, a footer, a row's trailing edge), make that room a named slot (`toolbar`, `actions`, `footer`; `header-actions` when there are several) and let the application put its own buttons, menus and filters there. Do not grow a built-in button with a flag to show it, a label property and an event for each command an app might want.
   - The component supplies what an action needs to do its work: public methods (`expandAll()`, `clearSelection()`), properties the action can set, and events that report the state an action reflects (`selection-change`, `sort-change`). An action in the zone is then a `c2-button` and one line of the app's code.
   - Build an action in only when the component cannot work without it or it is part of the widget's own keyboard and ARIA pattern (a dialog's close button, a column's sort toggle, a tree row's expander). A built-in action stays replaceable through a slot.
   - For an action per item, give the item an `actions` slot when items are authored in markup, or a narrow renderer (`renderActions` on `c2-tree`) when they come from data.
   - The zone is a slot like any other: hidden when empty, its wrapper exported as a `part`. Reference: `c2-table` and `c2-virtual-list` (`toolbar`, `footer`), and the `actions` slot of `c2-page-header`, `c2-dash-card`, `c2-banner` and `c2-tree-item`.

6. **Text a component draws is translatable through message tokens.** A component that shows or announces any text of its own (a label, a placeholder, an `aria-label`, a live-region announcement, a validation message, default slot content) lists each string under a key in `src/messages.ts`, registers it with `defineMessages('<package>', en)` and renders it with `this.msg.t('<key>', …args)` through a `LocalizeController`; an app translates by supplying the same keys with `addTranslations`. No string literal reaches the template. A text property keeps an empty default and falls back to its message, so setting it still overrides one instance; where an empty string must mean "show nothing" (an empty state, a placeholder), it defaults to `undefined` instead and falls back with `??`. "Built-in text is in English, and translatable" under "Component conventions" has the details. The gallery shows it: one card under a `lang` other than English.

**Scope.** Rule 1 and rule 4 apply to every component. Rule 5 applies to components with more than one region; rule 6 to any component that draws text of its own. Rule 2 applies wherever the component draws content the author may want to replace. Rule 3 applies to components that display a collection (lists, tables, trees, boards, charts, pickers); a button or a badge has no data form. Bringing an existing component up to these rules is additive: removing or renaming a public attribute, slot or property is still a breaking change that needs explicit sign-off.

**Variants are companion elements.** A request for more from a component is one of three things; decide which before writing code:

1. **A variant**, when it fixes what the component's items mean (a flowsheet is a table whose rows are measures and whose columns are times) and brings what the generic component does not need: a data shape of its own, structure derived from the data rather than declared, computations specific to a domain (a weighted final grade, a capacity per person and week) or domain chrome (a day label over the times, a "now" column). It is a companion element in the same package that extends the component, with its own source file, Vite entry, `exports` subpath, docs page and gallery, listed in the package's `c2n.separateEntries` so the umbrella gives it an entry of its own (`c2-group-table` and `c2-tree-table` extend `c2-table`; `c2-flowsheet` and `c2-allocation-grid` extend `c2-group-table`).
2. **A feature of the base**, when a component in another domain would want it too (for a table: sorting, selection, a summary row, filters, editing, paging, a column format). It loads lazily unless the first paint needs it, as the table's editing, filters and realtime modules do.
3. **An example**, when markup, a renderer or a preset of CSS variables already covers it: a gallery card on the page of the component or variant that does.

The base keeps only generic hooks a variant overrides (`c2-table`'s `resolvedColumns`, `sourceRows`, `cellValue`, `renderLine`) and never holds variant code; code two variants share lives in a module both import (`table-series.ts`). A variant can be removed without touching another page, and the base's pages never pay for it, which is why a feature only one variant uses moves out of the base even when it is small. `docs/planning/TABLE-VARIANTS.md` records how `@c2n/table`'s features were sorted this way (2026-11-14).
