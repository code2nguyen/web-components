Takeaways:

- Every shell has the same five regions: **banner** (environment / test-mode / impersonation strip), **header**, **navigation** (start), **aside** (end, optional) and **main**, with an optional **footer** / status bar.
- Two arrangements cover every product looked at: **header-first** (header spans the top; GitHub, Google Cloud, Carbon) and **navigation-first** (navigation runs full height and the header sits over main; Linear, Stripe, Notion). Mantine and Vaadin both expose exactly this switch.
- Navigation has three presentations, chosen per width: **side** (pushes content), **rail** (icons only, labels in tooltips), **over** (modal drawer). Phones are always `over` (or a bottom bar). Material's window size classes give the defaults: < 600 over, 600–959 rail, ≥ 960 side.
- The **toggle lives in the header** but controls the shell. Vaadin solves it with a `<vaadin-drawer-toggle>` element that finds its layout, Web Awesome renders the toggle itself, Mantine leaves it to the app.
- An app header is denser and more structured than a site header: a **context switcher** (workspace / org / project, often a breadcrumb of menus), a **search** that collapses to an icon on narrow widths, and **global actions** that overflow into a "More" menu. A site header (`c2-header`) has brand + primary nav + a few actions.
- The shell often owns app-wide services too (Polaris: toast, loading bar, unsaved-changes bar). c2 already has `c2-toast-region`; the shell should not absorb it.

## 2. What the repo does today

Three example apps hand-build a shell from `c2-header` + `c2-side-nav`:

| App                                            | What it hand-rolls                                                                                                                                                                                                                                         |
| ---------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `observability-nextjs` (`AppShell.tsx`)        | Skip link, `<main id tabIndex=-1>`, brand block (mark + name + subtitle), a polite live region, and the navigation toggle wired through React state + `useElementProperties` + an `opened-change` listener, because the toggle sits outside `c2-side-nav`. |
| `log-lens-nextjs` (`AppHeader.tsx`)            | Brand block, a ⌘K search button with a hand-built key hint, a row of quiet buttons with no overflow on narrow screens, `c2-theme-select`.                                                                                                                  |
| `close-workbench-sveltekit` (`+layout.svelte`) | Brand block (mark + company + period), `c2-navigation-menu` with count badges, status badge + theme select in `actions`; no side navigation at all.                                                                                                        |

Gaps that a shell and an app header would close:

1. **The toggle cannot reach the drawer.** `side-nav-toggle` only works on elements _inside_ `c2-side-nav`; a header above it needs app state. Every app with a drawer pays this.
2. **Skip link + main landmark** are rewritten each time (`c2-skip-link` exists but nothing places it or the `<main>` target).
3. **Brand block** (mark, product name, secondary line) is rebuilt with custom CSS in all three apps.
4. **No aside region** (details / inspector panel) and no banner region anywhere.
5. **Breakpoints follow the viewport**, so `c2-side-nav` inside a docs example frame or an embedded iframe picks the wrong mode. A shell should size from its own width (container), like `c2-masonry` does.
6. **Header actions do not collapse.** Log Lens' five actions wrap or overflow below ~720px.

## 3. Accessibility

- Landmarks: one `banner` (the app header), one `navigation` per nav region with a name ("Main", localisable), one `main`, optional `complementary` (aside) and `contentinfo` (footer). The shell renders the landmark elements in its shadow root around the slots, so authors write none. A `<header>` inside a shadow root still maps to `banner` when not inside `main` / `article` / `section`.
- Skip link first in tab order, targeting the shell's `main`, which takes `tabindex="-1"` and focus on activation (WCAG 2.4.1). Built in, label localised, overridable through a `skip-link` slot (Web Awesome does the same).
- Navigation in `over` mode is a modal dialog: focus trap, Escape, backdrop click, scroll lock, focus returns to the toggle. `c2-side-nav` already does all of it; reuse the code, do not fork it.
- The toggle is a button with `aria-expanded` and a name that says what it opens ("Open navigation" / "Close navigation"). `aria-controls` cannot point from the header's shadow root into the shell's; `aria-expanded` alone is what APG's disclosure pattern needs.
- Rail mode: icon-only items must keep their accessible name (the hidden label stays in the accessibility tree, a tooltip shows it on hover / focus).
- Closing the over drawer after a navigation (Vaadin's `closeDrawerOn`) so focus lands on the new page, not inside a dismissed drawer.
- Reduced motion: drawer slide and header hide-on-scroll respect `prefers-reduced-motion`.
- Hide-on-scroll headers (Mantine `useHeadroom`, M3) must reappear on focus inside them and never hide while a header menu is open.

## 5. Recommendation

- **`c2-app-shell`**: a new layout element with slots `banner`, `header`, `navigation`, `navigation-header`, `navigation-footer`, `aside`, `footer` and the default slot for main. Behaviour attributes: `layout="header-first | navigation-first"`, `navigation-opened`, `aside-opened`, `desktop-mode` / `tablet-mode` (`side | rail | over`, same vocabulary as `c2-side-nav` plus `rail`), `scroll="page | main"`, `header-behavior="static | sticky | hide-on-scroll"`, `close-on-navigate`. Breakpoints from the host's own width. Toggles: any descendant with `app-shell-toggle="navigation | aside"`, including inside a slotted header, so no script is needed. Sizes, colours and dividers are `--c2-app-shell__*` variables. `c2-side-nav` stays as the lighter "drawer + content" primitive; both share one drawer controller in `@c2n/core`.
- **`c2-app-header`**: a new element rather than more slots on `c2-header`, because its behaviour differs: a built-in navigation toggle that finds the enclosing shell (rendered only when the shell has navigation and is not in `side` mode, or always with `toggle="always"`), a `context` slot for the switcher / breadcrumb, a `search` slot that collapses to an icon button and expands over the bar on narrow widths, and an `actions` slot whose items move into an overflow menu when they do not fit (`overflow` attribute). Brand gets structure: `brand` slot plus `product-name` / `product-tagline` text props rendering the mark + name + secondary line every example rebuilt. Same `--c2-header`-style variable names where the concept is the same, mapped to the same theme tokens.
- `c2-page-header` (roadmap #58) stays separate: the page title, breadcrumbs and page actions belong to main, not to the app header (Vercel's tabs row is a page header).

## 6. Open questions

1. Container width or viewport for breakpoints? Container is more correct (iframes, docs frames, split views) but differs from `c2-side-nav`. Proposal: container, with `--c2-app-shell--tablet-breakpoint` / `desktop-breakpoint` variables… except breakpoints switch behaviour, so they may need to be attributes.
2. Bottom navigation on phones (Vaadin `touch-optimized`, M3 navigation bar): part of the shell (`navigation-placement="bottom"`) or the separate `c2-bottom-nav` (roadmap #66) placed in the `footer` slot? Proposal: the latter.
3. Should the shell remember the user's side / rail choice (`storage-key`, like `c2-theme-select`)? Most products do.
4. Overflow in `c2-app-header`: build it here, or build `c2-overflow-list` (roadmap #62) first and use it inside?
5. Header panels (Carbon right-edge panels for notifications / switcher): use the `aside` region, or `c2-sheet`? Proposal: `c2-sheet` / `c2-menu` anchored to the action; the aside is page content.
