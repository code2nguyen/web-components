# @c2n/mcp

Guidance for `packages/tools/mcp`. Claude Code loads this file when it works in this directory; the repo-wide rules are in the root `CLAUDE.md`. Paths are relative to the repository root.

`packages/tools/mcp` — `@c2n/mcp`, a published stdio MCP server (`bin: c2n-mcp`, `npx -y @c2n/mcp`). It exposes the components to AI agents through 11 tools (`list_components`, `search_components`, `get_component`, `get_examples`, `search_examples`, `get_presets`, `get_theme`, `generate_variant`, `validate_markup`, `report_issue`, `get_workflow_guide`) and `c2n://` resources over a bundled `data/registry.json` (generated during build/prepack, ignored by Git, prettier-ignored, no timestamp) built by `scripts/build-registry.ts` from every built package's `custom-elements.json`, the docs MDX (UsageBlock rows, gallery fences), `component-presets.ts`/`component-previews.ts`, the theme's `tokens.json` and the skill's hand-written reference guides. The generated skill catalog is excluded from registry inputs to prevent derived-data feedback. Gallery cards get a slug, a generated summary (`scripts/gallery.ts`), CSS whose neutral colours follow the theme (`themeExampleCss`: a colour role's exact light value becomes `var(--c2-theme--<role>, literal)`, property-aware so text takes `on-*` roles and surfaces never do; other opaque greys become an ink/paper `color-mix`; pale tints and the accent text on them become `light-dark()` pairs; mid-tone hues and blocks with a strong coloured background stay literal), and screenshot URLs under `<docs>/gallery-shots/<component>/<slug>.<light|dark>.png`. Those PNGs are written by `apps/ui/scripts/gallery-shots.mjs` (`pnpm run gallery:shots`, after `ui:build` and `build:tools`) in `deploy.yml` only: served by Pages, never committed or shipped in npm; the script skips a gallery whose page labels disagree with the registry order. `CHROMIUM_PATH` overrides the browser. The same walk is the **gallery audit** (`pnpm run gallery:audit [ids…]`, after `ui:build` + `build:tools`; opt-in because it is slow: the `Gallery audit` workflow runs from the Actions tab with an optional `components` input, or on a PR labelled `gallery-audit`, and the project skill `.claude/skills/gallery-audit` is how an agent runs and triages it): per card and theme it runs axe-core's `color-contrast` (with the canvas dot pattern removed, since axe cannot measure text over a gradient and silently passes it), and flags unregistered `c2-*` tags, cards with no visible box, content wider than the frame and console errors. Findings go to `test-results/gallery-audit/report.{json,md}` and are compared with `apps/ui/gallery-audit.known.json` (`<gallery>/<slug|*>/<theme>/<kind>` → reason): a new finding or a stale entry fails, so the list only shrinks; add an entry only for a problem you are deliberately deferring. Text axe cannot measure is reported as a count, never failed. `src/lib/validate.ts` is `validate_markup` and the `c2n-mcp validate` CLI (`src/validate-cli.ts`; `--hook` is the Claude Code `PostToolUse` hook `@c2n/skill` installs): a tolerant tag scanner, not a parser, over HTML/JSX/Vue/Svelte/Astro/Angular/Lit and CSS, checked against the registry (each element's `properties`, the public fields from its manifest, are what a property binding may set) with installed manifests overlaid; `scripts/validate.test.ts` covers it. Before tightening a rule, run it over `apps/examples` — everything it reports there should be a real bug. `src/lib/generate-code.ts` is the `generateCode` port (base class/module from the registry, which fixes `c2-tab` and icon tags). Runs unbuilt on Node 24 (`node src/cli.ts`, `erasableSyntaxOnly`); `dist/` is the published build. The root `.mcp.json` points local sessions in this repo at the source entry. **Discovery metadata:** `search_components` (`src/search.ts`) ranks by name, the docs frontmatter `keywords` (other names of the widget), the description and the frontmatter `intents` (3–5 requirement-worded sentences of what a developer wants done when the component is the right choice, without naming it; the best-matching one is printed with each hit, and `get_component` lists them as "Use it to:"), then the API and examples; icon-set names are searched only when the query mentions an icon (`icon`, `glyph`, `illustration`…, not `arrow`, which is keyboard navigation as often) or is itself an icon's name that no component carries (`trash`, not `pie chart`). That mix was measured on a blind set of requirements: intents generalized to new wording, more keywords did not, and icon names were noise (that set was then retired, since the design was chosen on it, and replaced by a fresh one). `pnpm run mcp:readiness` scores discovery against three sets: `scripts/readiness/tasks.json` (the headline, tune against it), the lab requirements, and `scripts/readiness/heldout.json` (written blind, only its numbers printed): never tune against the held-out set, since a gain on `tasks.json` with none there is overfitting.
