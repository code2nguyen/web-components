# Example apps

Guidance for `apps/examples/*`. Claude Code loads this file when it works in this directory; the repo-wide rules are in the root `CLAUDE.md`. Paths are relative to the repository root.

`apps/examples/*` — **example apps**: complete applications that consume the published packages the way an outside project would (its own Vite build, its own dependencies, its own custom element registry). One directory per app, each with an `app.config.json` (`title`/`description`/`framework`/`tags`/`order`) that the docs site loads directly as the `examples` Content Layer collection — the metadata has exactly one home, so adding an app is a directory drop plus a wireit entry. Because the apps import sibling components, every `@c2n/*` they use must be listed in the package's **`type-check`** dependencies (not just `build`), or a clean build type-checks the app before those declarations exist. Each app builds into its own `dist/` (wireit refuses to track output outside the package that produced it) and `apps/ui/scripts/sync-examples.mjs` copies the results into `apps/ui/public/demo/<id>/` from the `pre{build,dev,start}` scripts of `apps/ui`: Astro serves `public/` in dev and copies it verbatim into `dist/` on build, so dev and Pages share one URL and `deploy.yml`'s artifact path is unchanged. Two things bite: each app's Vite `base` **must** be `/web-components/demo/<id>/` (a wrong base works in dev and 404s on Pages), and the running apps live under `/demo/`, not `/examples/`, because a public file at `public/examples/<id>/index.html` silently shadows the `/examples/<id>` docs route. The build output is gitignored and excluded from prettier and eslint. The docs side is `src/pages/examples/index.astro` (cards grouped by framework) and `[exampleId].astro`, which embeds the app in an **iframe** — not only for CSS isolation: two demos in one document share one `CustomElementRegistry` and the second `customElements.define('c2-button', …)` throws. The page hands the iframe the site's resolved theme through `?theme=`, which the app applies before first paint, and re-points it on the `c2n-theme-change` event.

- **React examples** (`trading-dashboard-react`): React 19 + `@vitejs/plugin-react` (the Babel/oxc plugin, **not** `-swc` — that would add `@swc/core-linux-*` native binaries and the lockfile would need new pins, see "Linux native binaries"). Three things a React consumer has to do, all shown there: (1) `src/c2-elements.d.ts` maps the tags into JSX — the packages declare `HTMLElementTagNameMap`, which JSX does not read — deriving props as `DetailedHTMLProps<HTMLAttributes<T>, T> & Partial<Omit<T, keyof HTMLElement>>` from each element class; (2) the elements must be **registered at module scope before React renders**, or React sets an object prop such as `rows` as an attribute and it stringifies; (3) kebab-case custom events (`selection-change`) have no `on*` spelling in JSX, so they go through a ref and `addEventListener` (`src/hooks/useCustomEvent.ts`) — as does `input`/`change`, since React's `onChange` is its own synthetic form-control event. A row type handed to `c2-table`'s `rows` needs an index signature (`TableRow` is `Record<string, unknown>`), and `renderCell` is handed to Lit so it cannot return JSX — return a DOM node instead, and colour it through an inherited custom property, since a stylesheet in the document cannot reach into the table's shadow root.

- **Angular examples** (`orders-admin-angular`): Angular 22 (zoneless, standalone, signals) built by the Angular CLI — `@angular/build:application` through `angular.json`, so this is the one example whose `build` command is `ng build` rather than `vite build`, and the one with **no separate `type-check` script**: `ng build` runs `ngtsc`, which type-checks the templates as well, so the sibling `@c2n/*` builds hang off `build` directly. Angular 22 requires `typescript >=6.0 <6.1`, which the repo's pinned 6.0.3 satisfies — check that first when bumping either. The app's `tsconfig.app.json` overrides the shared lib config (`noEmit`, no declarations, ES2022); `src/styles.css` pulls the theme in with `@import '@c2n/theme/theme.css'` and `baseHref` in `angular.json` plays the role Vite's `base` plays elsewhere. Interop is the cleanest of the three: `CUSTOM_ELEMENTS_SCHEMA` on the component is the only configuration, `[rows]="…"` writes a property through `setProperty`, and `(selection-change)`/`(row-click)` bind kebab-case custom events by their real name. The trap is the reverse of React's: a **static** attribute in an Angular template stays an attribute, so `rowKey="id"` sets `rowkey`, which the component only picks up through the element helper's forwarding (with a warning) — camelCase properties need `[rowKey]="'id'"` or the component's real attribute name (`row-key`). Server-rendered React (Next.js) has the same trap: the server writes props verbatim as attributes and hydration sets no properties. Cost to be aware of: Angular adds ~100 lockfile entries and several native-binary families (`@lmdb/*`, `@napi-rs/nice-*`, `@oxc-parser/*`, a nested `@rolldown/binding-*`), all of which npm recorded for every platform — unlike the root `@rolldown`/esbuild pins — so no new entries in `optionalDependencies` were needed. Verify that again after an Angular major bump.

- **Vue examples** (`support-inbox-vue`): Vue 3 SFCs (`<script setup lang="ts">`) + `@vitejs/plugin-vue`, type-checked by **`vue-tsc`** rather than `tsc` — that is the only difference in the package shape, since plain `tsc` cannot read a `.vue` file. The one required piece of configuration is `template.compilerOptions.isCustomElement = (tag) => tag.startsWith('c2-')` in `vite.config.ts`; without it the compiler resolves every `c2-*` tag as a Vue component, warns and renders nothing. Vue picks between a property and an attribute with **`key in el`**, so registering the elements before `mount()` is what makes plain bindings land as properties — and gives two explicit escape hatches, both shown in the app: `.prop` for array/object values (`:value.prop="[activeId]"` on `c2-list`/`c2-select`) and `.attr` for the reverse trap, a property the component does **not** reflect but styles through `:host([attr])` — `c2-chat-message`'s `align` is exactly that, so it is bound as `:align.attr` or it is silently inert. Kebab-case custom events bind by their real name (`@selection-change`), the handler receiving a plain `Event` to narrow. `v-model` works on `c2-text-field`/`c2-textarea`: on a custom element Vue compiles it to the plain-text model directive, which sets `el.value` and listens for `input`, and both components expose `value` and re-emit the inner control's native `input` through `redispatchEvent`. Vue's template type-checking of the tags themselves is off by default (`strictTemplates`), so unknown elements are accepted — there is no JSX-style declaration file to maintain as there is for React. Cost: ~25 lockfile entries and no native binaries.

- **SvelteKit examples** (`close-workbench-sveltekit`): SvelteKit 3 + Svelte 5 (runes), every route prerendered by `@sveltejs/adapter-static` into `dist/` with `paths.base` set in the `sveltekit()` Vite plugin — SvelteKit 3 has no `svelte.config.js`, its tsconfig extends `$app/tsconfig`, `$lib` is gone in favour of the `#lib/*` subpath import in `package.json`, and `$app/environment` is now `$app/env`. `type-check` is `svelte-kit sync && svelte-check --fail-on-warnings`. Elements are registered from `init` in `src/hooks.client.ts` (awaited before hydration, never on the server). Prerendering writes attributes only, so array props go through `data()` in `src/lib/ssr.ts` (JSON on the server, the value in the browser) and function props (`renderItem`, `rowPart`) through `{@attach}`. Svelte's two click-handler a11y warnings are filtered for `c2-*` tags in `vite.config.ts` (it cannot see the button in the shadow root). The domain (matching engine, exception classifier, journal, reconciliation) is DOM-free erasable TS in `src/lib/close/` with `node --test` units in `test/unit/`; `test/browser/` is a Playwright suite against `vite preview` of the build, wired into `examples-tests.yml`. `.svelte` files are outside the prettier and eslint globs (no `prettier-plugin-svelte`), like `.astro`: format them by hand; `svelte-check` covers their types. Cost: ~25 lockfile entries, no native binaries.

- **Next.js log analyzer** (`log-lens-nextjs`): an OpenTelemetry log analyzer on the same Next.js shape as `observability-nextjs` (static export, `outputDir: "out"`, `C2Registry` + `useElementProperties` + `useCustomEvent`, generated `/react` JSX types in `types/`, which needs its own `!apps/examples/log-lens-nextjs/types/` line in `.gitignore`). The analysis is plain erasable TS in `lib/` (OTLP JSON/JSONL parser, Drain-style pattern mining, story chapters, trace divergence, attribute lift) with `node --test` unit tests over the deterministic sample in `lib/sample.ts`; keep UI logic out of `lib/` so those tests stay browser-free.

- **Astro examples** (`wayline-marketing-astro`): a static Astro 7 landing page (the roadmap's "Marketing site"), `astro build` into `dist/` with `base` set to the demo path; `type-check` is plain `tsc` over the `.ts` files (no `@astrojs/check`, which would add dependencies), and the `.astro` templates stay markup. The `c2-*` tags are plain custom elements registered by a bundled `<script>` — no `@astrojs/lit` SSR — and below-the-fold modules load through `src/scripts/islands.ts` when their section nears the viewport. Astro writes boolean props on custom elements as `"true"`/`"false"`, which `@c2n/core`'s converter reads correctly. Astro 7 backgrounds `astro preview` when it detects an AI agent, so the Playwright `webServer` sets `ASTRO_PREVIEW_BACKGROUND` to keep it in the foreground. `.astro` files are outside the prettier glob: format them by hand. Cost: no new lockfile packages (Astro is already pinned by `apps/ui`).
