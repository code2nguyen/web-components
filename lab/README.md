# Component lab

The lab uses c2n components the way a real product does, then tests that product the way people use it. It has two
goals:

1. **Find component bugs**: problems a component's own suite misses because they only show up in a real app, with real
   input, a keyboard, a phone, a screen reader, dark mode or another language.
2. **Collect API feedback**: friction an app builder hits (workarounds, missing hooks, confusing defaults), filed in
   [`COMPONENT-FEEDBACK.md`](../COMPONENT-FEEDBACK.md).

Apps are disposable: what the lab keeps is the **spec**. A spec describes an app (or one screen of one) as
requirements tagged with shared capabilities. An agent builds it from the spec with the components, writes a **build
report** saying how each requirement was met, and the lab tests the build like a person would. The reports of every
spec add up in the **gap matrix**: where the components fall short of what real apps need.

It runs without a person. An agent (Claude Code, through the [`component-lab` skill](../.claude/skills/component-lab/SKILL.md))
explores and triages. The **oracles** below decide what counts as a finding: they are deterministic, so every finding
can be replayed and confirmed instead of trusted.

## Pieces

| Path                                      | What it is                                                                                        |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------- |
| `capabilities.md`                         | The shared tag vocabulary for requirements (`filter.range`, `form.validation`, …)                 |
| `specs/{scenarios,features,apps}/<id>.md` | Specs, from one screen to a whole product; `specs/TEMPLATE.md` is the shape                       |
| `apps/<id>/<direction>/`                  | Builds of a spec, one per design direction. Disposable, but committed so findings can be replayed |
| `reports/<id>/<direction>.md`             | Build reports: each requirement met, worked around, hand-rolled or failed; `reports/TEMPLATE.md`  |
| `reports/<id>/<direction>.calls.jsonl`    | The c2n MCP calls the builder made, read by `scripts/readiness.mjs` (see AI readiness below)      |
| `GAPS.md`                                 | The gap matrix, generated by `scripts/gaps.mjs`                                                   |
| `targets/<name>.json`                     | What the runner tests: an app's URL, how to start it, and its **journeys** (one per spec task)    |
| `scripts/lab.mjs`                         | The runner: every journey × every persona, the oracles watching                                   |
| `scripts/lib/personas.mjs`                | Who is using the app, and how a step becomes real input for them                                  |
| `scripts/lib/steps.mjs`                   | The journey step language                                                                         |
| `scripts/lib/oracles.mjs`                 | Console, uncaught errors, failed requests, axe, overflow, the focus indicator check               |
| `scripts/lib/ax-tree.mjs`                 | Chrome's accessibility tree (what a screen reader gets), and the checks read from it              |
| `known.json`                              | Findings already triaged (`key → reason`): a ratchet, it only shrinks as components get fixed     |
| `runs/<date>-<target>.json`               | Run records: the history of the lab, one file per recorded run (see "Run records and replay")     |
| `scripts/lib/record.mjs`                  | Builds, compares and writes run records                                                           |

## Specs, builds and the gap matrix

Specs come in three sizes. A **scenario** is one screen around a few components (it may name them in `focus`); a
**feature** is one flow; an **app** is a whole product, and does not name components, since choosing them is part of
the test. A spec can list several **design directions** (the shipped theme, a dense admin, a strong brand); each is a
separate build styled only through tokens, component variables and documented parts.

```
spec ──build (agent + c2n MCP)──▶ lab/apps/<id>/<direction>/ ──▶ build report (met / workaround / hand-rolled / failed)
  │                                        │
  └── tasks ──▶ journeys (targets/<id>.json) ──▶ lab run (personas × oracles) ──▶ findings
                                                                  reports ──▶ gaps.mjs ──▶ GAPS.md
```

`node lab/scripts/gaps.mjs` rebuilds `GAPS.md`: builds per spec, capabilities ranked by how far the components fall
short, the shortfalls filed under each component, and coverage (capabilities no spec requires, components no report
names: what to write the next spec about). `--check` exits 1 on an unknown tag, a missing report row or a bad outcome.

A lab app is plain files served by Vite from the repository root (`npx vite lab/apps/<id>/<direction>`), importing
`@c2n/components/*` like any consumer: build the umbrella first (`npm run build -w packages/umbrella`, or any example
app's build). Pick a port outside the browsers' unsafe-port list (4190 is on it).

## AI readiness

Each build also measures how an agent finds the components, for the AI readiness score
(`packages/tools/mcp/readiness/`, the `ai-readiness` skill):

- **While building**, this repository's `.mcp.json` (and `.codex/config.toml`) start the `c2n` MCP server with `C2N_MCP_LOG` set (a path relative to the repository root, like the server's own path
  in those files: both assume the session starts there), so it appends
  every call to `lab/.armed/mcp-calls.jsonl` (ignored) **while that file exists**: `readiness.mjs --arm <id>/<direction>`
  creates it when a build starts and `--disarm <id>/<direction>` deletes it after, so the log costs nothing the rest of the time. An entry holds
  the tool, its arguments (search words and options as written, and committed with the report; code and other free
  text by length only), the components a search returned and what `validate_markup`
  reported.
- **When the build is done**, `node lab/scripts/readiness.mjs --end <id>/<direction>` closes its window, so the calls of the
  lab run and the triage that follow are not counted.
- **After building**, `node lab/scripts/readiness.mjs <id>/<direction> --log lab/.armed/mcp-calls.jsonl` (`--since <time>`,
  by default the start `node lab/scripts/readiness.mjs --arm <id>/<direction>` recorded, refused for another report;
  the builder marks its server with a `search_components` call for `c2n-lab <id>/<direction>` right after arming, and only
  that server's calls are kept (`--pid a,b` names them when there is no marker or the server restarted); `--disarm <id>/<direction>` after the report)
  keeps the build's calls (every session in the repository writes to that file; each entry carries its server's `pid`,
  and nothing is kept without a marker or `--pid`) as `reports/<id>/<direction>.calls.jsonl` and writes the report's generated **AI readiness** section: the search
  that found each component the build used (or none), components used without `get_component`, searches that found
  none of them, and `validate_markup` on the build as it is now. `--all` regenerates every report from its committed
  log; `--check` exits 1 when a section is stale (a `component-tests.yml` gate on pull requests: a component change
  that breaks a lab build's markup shows there).
- **The requirements** feed the readiness run: every `met` or `workaround` row becomes a discovery requirement (the
  spec's words, the components the report names; generic buttons and badges, and `a11y.*`/`theme.*` rows, left out),
  reported as "Lab requirements" next to the benchmark and kept out of the headline. Nobody tuned the search for a
  spec's words, so a miss there is how a developer would really phrase the need.

## The weekly run

Once a week, when there is budget, start a Claude Code session in this repository and say "run the component lab".
The `component-lab` skill then reruns every target (regressions first), builds the next unbuilt spec, refreshes
`GAPS.md` and opens a pull request with what it found. Its "The weekly run" section has the steps.

## Run records and replay

The lab keeps its history in the repository: `lab/runs/` holds one JSON file per recorded run, committed with the
code it tested. A record has:

- **the library under test:** `lerna.json` version, commit, branch, and whether component sources had local edits;
- **the runner:** personas, repeat count, journeys, and whether it was a **full** run (every persona and journey);
- **the build:** for a target built from a spec, a snapshot of its build report's outcomes (`R1: met`, …) at the time;
- **results:** each journey × persona with its runs and passes, and every finding with its key, status (new or known)
  and whether every repeat saw it;
- **change:** compared with the target's previous full run, the findings that appeared or are gone and the journeys
  that started or stopped passing.

`node lab/scripts/lab.mjs replay` is the regression check: every target (or `--targets a,b`), twice, recorded and
compared, then a summary (also written to `test-results/lab/replay-summary.md`) that lists known findings no longer
seen, the component fixes to confirm. It needs no AI, so the **Component lab replay** workflow
(`.github/workflows/lab-replay.yml`) runs it weekly and from the Actions tab, with the records and reports in its
artifact. Records are committed by the lab session that triages them, not by CI.

`node lab/scripts/lab.mjs run <target> --record` records a single run, for a new build's first run. Ad-hoc `--steps`
runs are never recorded.

## The lab on the docs site

The docs site shows the lab at `/lab` (`apps/ui/src/pages/lab/`), linked from the footer: the latest run of every
target, the gap matrix, the open findings by component (linked to their docs pages) and the specs; each spec has a page
at `/lab/specs/<id>` with its requirements and each build's outcome, the journeys × personas of its latest run, and its
run history. The site reads `lab/runs/*.json`, `lab/specs/**/*.md`, `lab/reports/*/*.md` and `lab/capabilities.md` at
build time through content collections (`apps/ui/src/content.config.ts`, `src/data/lab.ts`) and never runs the lab, so a
merged lab PR shows up with the next deploy. A malformed run record fails the site build on its schema
(`labRunSchema` in `apps/ui/src/schemas/index.ts`): change the two together.

## Run it

```bash
npm run build -w apps/examples/support-inbox-vue       # the app and the components it uses (wireit-cached)
node lab/scripts/lab.mjs list                          # targets, journeys, personas
node lab/scripts/lab.mjs run support-inbox-vue         # every persona × every journey
node lab/scripts/lab.mjs run support-inbox-vue --personas keyboard --journeys filter --repeat 3
node lab/scripts/lab.mjs run support-inbox-vue --personas mouse --steps my-steps.json --aria   # ad-hoc exploration
node lab/scripts/lab.mjs replay                        # every target, twice, recorded in lab/runs/ and compared
```

The runner starts the app's dev server when nothing answers at the target URL. In a container with a preinstalled
Chromium, set `CHROMIUM_PATH` (the session-start hook does). Output goes to `test-results/lab/<target>/`:
`report.md`, `findings.json`, `shots/` (end-of-journey screenshots, failure and focus clips) and `snapshots/`
(accessibility trees). The exit code is 1 when a **new, reproducible** finding appears.

## Personas

| Persona    | Set-up                                       | Input                                                                              |
| ---------- | -------------------------------------------- | ---------------------------------------------------------------------------------- |
| `mouse`    | desktop 1280×800                             | pointer clicks (Playwright hit-tests them), typing key by key                      |
| `keyboard` | desktop 1280×800                             | Tab to a control, arrow keys inside a widget, Enter/Space; checks every focus ring |
| `mobile`   | Pixel 7, touch                               | taps                                                                               |
| `dark`     | `prefers-color-scheme: dark`, `data-theme`   | pointer                                                                            |
| `fr`       | `fr-FR` locale, Paris time zone, `lang="fr"` | pointer                                                                            |

No step calls `el.click()` or assigns `.value`. Those shortcuts hide real bugs (a host that ignores a click, an overlay
that catches it), so every action goes through the browser's input pipeline.

## Journeys

A journey is a user task written as steps that name what a person **sees**, never a path into a shadow root:

```json
{ "fill": { "role": "textbox", "name": "Reply" }, "text": "Thanks!" }
{ "click": { "ax": "option", "name": "Closed", "exact": true } }
{ "expect": { "visible": { "text": "Reply sent." } } }
```

Steps: `goto`, `click`, `fill` (+ `text`), `press`, `type`, `hover`, `wait`, `snapshot` (+ label) and `expect` with
`visible` / `hidden` / `focused` / `count` (+ `equals`) / `text` (+ `contains`) / `value` (+ `equals`).

Targets, most faithful first:

- `{ ax, name }`: the role and name from Chrome's accessibility tree. Use it for every role a component states through
  `ElementInternals` (c2-list rows are `option`s, c2-sheet is a `dialog`). Playwright's `getByRole` cannot see those
  roles, so a check built on it reports bugs that are not there.
- `{ role, name }`, `{ label }`, `{ placeholder }`, `{ text }`: Playwright's locators.
- `{ css }`: last resort. Needing it is itself worth a note: the thing has no accessible handle.

Any target takes `nth` and `within`. A journey can list `personas` to run for only some of them.

## Oracles

| Kind                                                                          | Fires when                                                                                                   |
| ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| `journey-broken`                                                              | a step could not be done or an expectation failed: the task did not work for this persona                    |
| `keyboard-unreachable`                                                        | neither Tab nor the arrow keys reach a control                                                               |
| `focus-invisible`                                                             | moving focus onto a control changes no pixel of it (compared across the component's whole box)               |
| `a11y-tree`                                                                   | the screen reader tree has something a person would notice: a name read twice, an invisible disabled control |
| `axe`                                                                         | an axe-core violation, attributed to the innermost `c2-*` host                                               |
| `overflow`                                                                    | the page scrolls sideways                                                                                    |
| `console-error` / `console-warning` / `uncaught-exception` / `request-failed` | what it says; warnings only when they mention a component, Lit or ARIA                                       |

Each finding is keyed `<target>/<kind>/<component>/<rule>` and merged across personas and journeys. Run with
`--repeat N` to separate reproducible findings from flaky ones.

## Adding a target

Write `targets/<name>.json` for any app under `apps/examples/` (or a new clone app built only from c2n): its URL, the
dev server command, the components it uses, and journeys covering the tasks a person does there. Start with a
`--aria` run of `[{ "goto": "./" }]` to read the accessibility tree, then write steps against the names you see.
