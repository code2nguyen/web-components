`c2-steps` is a list of `c2-step` rows — vertical by default, or side by side with `orientation="horizontal"`. Each row is a marker, a label, an optional dimmed `detail` beside
it and `trailing` text at the end — a duration, a count, a timestamp.

**A step with sub-steps is a group, and a group is a disclosure**: its own row is the summary and its sub-steps are
the detail. There is no second element to learn — the same tag is a leaf or a group depending on what is inside it.
That is what makes a long run readable: the list keeps the shape of the task while the detail of each stage stays
one click away.

**Every step is a row, and every row is visible.** A group starts expanded and nothing ever folds one away on its
own: the chevron is there for the reader, and `collapsed` in the markup starts a stage folded. The run only ever
brings a folded stage _back_ into view — one the reader put away reopens when it starts running (`running`,
`current`) or when something in it goes wrong (`error`, `warning`).

**A step is one row.** Label, detail and trailing text sit on a single line and truncate with an ellipsis rather
than wrapping, so a hundred-step trace stays scannable. A sub-step is indented by exactly the marker's width plus
the row gap, so its marker lands under its parent's label — that alignment is all the nesting needs, and nothing
else is drawn for it. `--c2-step__guide--width: 1px` adds file-tree rules if you want them, and the `toggle` slot
adds a chevron; both are off by default.

The detail sits **beside** the label by default, which is what a trace wants — a path or an id read as an aside to
the name. `--c2-step__text--flex-direction: column` puts it on its own line underneath instead, which is what a
wizard's descriptions want. That one variable is the whole switch: the gap between them and their alignment follow
it. Two lines on purpose, and each of them is still one line.

**A parent takes the status of the worst thing inside it** when it authors none of its own, so a stage reports that
it is running, or that something under it failed, without you setting it.

Author it either way, and mix them freely: slot `c2-step` children, or hand `c2-steps` a `steps` array of
`{ id, label, detail, trailing, status, reason, children }` and it renders the tree itself. The array wins when both are
present.

The connector rail is off by default, because a trace does not want one. Give `--c2-step__rail--width` a width and a
stepper gets its rail. Numbering follows the tree: `marker="number"` draws a dotted path, so the first child of the
third step reads `3.1` rather than a second `1`.

**Horizontal.** `orientation="horizontal"` lays the top-level steps out side by side, each a column with its marker
on a connector rail and its text underneath. **The rail always links one step to the next**: it starts right after a
step's marker and runs through the gap to where the next step begins, whatever the widths and paddings
(`--c2-step__rail__horizontal--width`, `2px`, sets its thickness). Sub-steps are not drawn in a horizontal list, but a
group still takes their status, so a stage reads as running or failed.

**The text can sit anywhere around the marker** — under it, over it, after it or before it. That is one variable,
`--c2-step__row__horizontal--grid-template-areas`, naming where the `marker`, `rail`, `text` and `trailing` cells go
on a three-column grid (`auto auto 1fr`). The rail always takes the last column, so it still links the steps:

| Text                | `--c2-step__row__horizontal--grid-template-areas`                                                                         |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| under (the default) | `"marker rail rail" "text text text" "trailing trailing trailing"`                                                        |
| over                | `"text text text" "trailing trailing trailing" "marker rail rail"`, with `--c2-step__row__horizontal--align-content: end` |
| after the marker    | `"marker text rail" ". trailing ."`                                                                                       |
| before the marker   | `"text marker rail" "trailing . ."`                                                                                       |

Every marker of a list hangs from the same line, so the rails line up from step to step whatever text each one has.

**Interactive.** `interactive` turns every row that is not a disclosure into a button, and the list keeps one
selected step — see [Selecting a step](#selecting-a-step).


## Selecting a step

A list of steps is often the navigation of the view under it: a task with a **Process** step and a **Result** step
shows the log while it runs and the result once it is done — and the reader should be able to go back to the log at
any time. `interactive` is that:

- Every row that is not a disclosure becomes a `<button>`. A group's row in a vertical list stays its disclosure.
- The list keeps one selected step in `selected`, named by the step's `value` (a data node's `id`) or, when it has
  none, by its dotted path (`2`, `1.3`). The selected row only changes its label colour
  (`--c2-step__label__selected--color`); `--c2-step__row__selected--background`,
  `--c2-step__row__selected--box-shadow` and `--c2-step__label__selected--font-weight` add more when a design wants
  it. It is announced with `aria-current`.
- Pressing a step selects it and fires `selection-change` with `{ value, path }`. Setting `selected` (or calling
  `select(value)`) moves the selection from code; only `select()` fires the event.
- `disabled` keeps a step from being selected — a result that does not exist yet.
- Selection is independent of `status`. The list never moves it on its own, so the run decides when the view
  switches, and the reader's choice is never taken away from them.

```html tag=CodeBlock
<c2-steps orientation="horizontal" interactive selected="process" aria-label="Task">
  <c2-step value="process" status="running" label="Process"></c2-step>
```

## Task lists and stage paths

A **task list** is a process the reader works through in any order: sections of tasks, each a link to its own page
with a status tag, and a line saying how far they have got. Three things make `c2-steps` one:

- `href` on a `c2-step` (or on a node of `steps`) makes its row a link. A group's row stays its disclosure, and a
  `disabled` step is drawn without its link — a task that cannot start yet. Links are in the tab order like any
  other; in an `interactive` list, following one also selects its step.
- `summary` adds a line above the steps — "2 of 5 completed" — counting every step that is not a group;
  `success`, `warning` and `skipped` count as done. The text is the `summary` message, translatable with
  `addTranslations({ fr: { steps: { summary: '{0} sur {1} terminées' } } })`, and the `summary` slot replaces it.
  `progress` returns the same `{ completed, total }` for a progress bar of your own.
- The status tag is a `c2-badge` in the `trailing` slot, or from `renderTrailing` for a list built from data.
  `marker="none"` drops the status glyphs when the tags say it already.

A **stage path** is the lifecycle of a record across the top of its page — Prospecting, Qualification, Proposal,
Closed. It is a horizontal, `interactive` list with `current` on the stage the record is in: the stages before it
read as done and the ones after as future. The chevrons are `--c2-step__row--clip-path` with the rail turned off,
and each status fills its row through page CSS on the step's state (`c2-step:state(current)`). An end state is an
explicit status on the last stage — `current` past the end makes every stage `success` (closed won), and
`status="error"` on the last one is closed lost.

The **header**'s `actions` slot is where the app puts its commands, beside the summary: "Mark as current stage" on a
stage path is one line that sets `current` from `selected`, and "Expand all" on a trace calls `expandAll()`. The
header is not drawn until `summary` is set or one of its slots is filled.

```js tag=CodeBlock
path.querySelector('[slot="actions"]').addEventListener('click', () => {
  const index = Number(path.querySelector(`c2-step[value="${path.selected}"]`).path) - 1
  if (index >= 0) path.current = index
})
```

## Lesson lists

A **lesson list** is a course's curriculum: sections of lessons, how far the reader has got through each section, and
lessons that cannot be opened yet. It is a task list with two more pieces:

- `group-progress` on `c2-steps` counts every group's finished steps and shows the count under the group's label —
  "2 of 5". It counts as `progress` does: the group's steps that are not groups themselves, with `success`, `warning`
  and `skipped` as done. `--c2-step__progress__bar--width: 64px` adds a bar in front of the count (filled in
  `--c2-step__progress__bar--color`, the success colour by default), and the text is the `groupProgress` message,
  translatable like the summary. Each group's `{ completed, total }` is its `progress` property, and a renderer reads it
  from `context.progress`.
- `status="locked"` is a step the reader cannot open yet. Its marker is a padlock, its label is muted
  (`--c2-step__locked--color`), and its row is neither a link nor, in an `interactive` list, selectable — `select()`
  refuses it too. Assistive technology hears "Locked" after the label (the `locked` message).
- `reason` (or the `reason` slot) puts a line under the label that says why: "Finish Getting started to unlock",
  "Available on 3 May". It works with any status — why a step was skipped, what a failure means. A group whose only
  unfinished steps are locked rolls up as `locked`.

The lesson's type is an icon in the `marker` slot (or from `renderMarker`), its duration the `trailing` text.

```html tag=CodeBlock
<c2-steps group-progress aria-label="Course content">
  <c2-step label="Getting started">
    <c2-step status="success" label="Welcome" href="/lessons/welcome" trailing="2 min"></c2-step>
    <c2-step status="current" label="Your first form" href="/lessons/form" trailing="12 min"></c2-step>
  </c2-step>
  <c2-step label="Theming">
    <c2-step status="locked" label="Design tokens" reason="Finish Getting started to unlock"></c2-step>
  </c2-step>
</c2-steps>
```

## Driving a run

A trace usually arrives as data. Hand over the shape of the task once, then tick one step at a time — `updateStep`
finds a step by `id` and redraws without rebuilding the array, which is what a runner wants when it fires hundreds
of times:

```js tag=CodeBlock
const trace = document.querySelector('c2-steps')

trace.steps = [
  { id: 'build', label: 'build', children: [{ id: 'install', label: 'install dependencies' }, { id: 'compile', label: 'compile' }] },
  { id: 'test', label: 'test', children: [{ id: 'unit', label: 'unit' }, { id: 'e2e', label: 'e2e' }] },
]

// The parent stage rolls the status up on its own.
trace.updateStep('install', { status: 'running' })
trace.updateStep('install', { status: 'success', trailing: '19 s' })
```

Nothing stops you doing the same to slotted markup — a `c2-step` is an element, and setting `status` on it is
enough — as a property or an attribute. The step tells its list, so a stage rolls its status up from that alone:

```js tag=CodeBlock
document.querySelector('c2-step[data-id="e2e"]').status = 'running'
```

### What moves while it runs

A trace being written in front of you should look like it. Two things move, and neither needs anything from you:

- **A step that arrives** while the list is already on screen grows into place from a collapsed row and fades in,
  rather than snapping the rows below it down the page. A step drawn with the list does not — a whole trace fading
  in at once is a page loading, not an arrival.
- **A status that settles** gives its marker one beat. Again only a status that actually _changed_: a trace
  rendered complete sits still.

`--c2-step--enter-duration` (`260ms`) and `--c2-step--enter-translate` (`-4px`) shape the arrival, and `0s` turns
it off; `--c2-step--transition-duration` (`150ms`) covers the colour transitions and the beat.
`prefers-reduced-motion: reduce` turns all of it off.

Give every node a stable `id`. That is what lets the list reuse a step's DOM across renders instead of rebuilding
it — without one a step is identified by its position, so inserting anywhere but the end recreates the rows after
it, and they all animate in as if they were new.

`collapseAll()` folds every group away, leaving the top-level stages; `expandAll()` brings them all back.

A group announces itself when it is folded away or brought back. The event bubbles, so one listener on the list
hears them all:

```js tag=CodeBlock
trace.addEventListener('step-toggle', (event) => {
  console.log(event.target.label, event.detail.path, event.detail.collapsed)
})
```

## Styling by state

A step never writes an attribute on its own host, so server-rendered markup matches the hydrated element:
neither the `status` the list rolls up nor a `collapsed` the reader toggles is reflected. Page CSS reads a step
through its custom states instead:

| State                                                                                                                             | When                                                         |
| --------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| `:state(pending)`, `:state(running)`, `:state(current)`, `:state(success)`, `:state(error)`, `:state(warning)`, `:state(skipped)` | The step's current status, authored or rolled up             |
| `:state(collapsed)`                                                                                                               | A group is folded away                                       |
| `:state(has-children)`                                                                                                            | The step has sub-steps, so it is a group                     |
| `:state(last)`                                                                                                                    | The last step of its group                                   |
| `:state(grouped)`                                                                                                                 | The list holds a group anywhere                              |
| `:state(marker-icon)`, `:state(marker-number)`, `:state(marker-none)`                                                             | The list's `marker` mode                                     |
| `:state(entering)`                                                                                                                | A step that arrived in a running trace is growing into place |
| `:state(settling)`                                                                                                                | Its marker is giving the beat of a status that changed       |

```css tag=CodeBlock
c2-step:state(error) {
  --c2-step__row--background: #fef2f2;
}
```

Earlier releases wrote `entering`, `settling`, `last`, `marker`, `grouped` and `has-children` attributes on the
host and reflected `status` and `collapsed`; replace `c2-step[last]` with `c2-step:state(last)`,
`c2-step[marker='number']` with `c2-step:state(marker-number)`, `c2-step[status='error']` with
`c2-step:state(error)`, and likewise for the others. An authored `status` or `collapsed` attribute still works.

## Rendering a row yourself

Everything the markup fills with a slot, the data-driven mode fills with a renderer — the two modes have the same
reach, and a renderer is simply the function form of the slot:

| Part of the row           | In markup                | From `steps`     |
| ------------------------- | ------------------------ | ---------------- |
| the icon                  | `<span slot="marker">`   | `renderMarker`   |
| the primary text          | `<span slot="label">`    | `renderLabel`    |
| the dimmed text beside it | `<span slot="detail">`   | `renderDetail`   |
| the text at the end       | `<span slot="trailing">` | `renderTrailing` |
| the disclosure affordance | `<span slot="toggle">`   | `renderToggle`   |
| all of the text at once   | —                        | `renderItem`     |

Every renderer is handed the node, its depth, its position, its dotted path and the status actually in effect, and
returns anything Lit renders — a string, an `<svg>`, an icon element:

```js tag=CodeBlock
import '@c2n/feather-icons/icons/alert-triangle.js'
import { html } from 'lit'

// An icon of your own instead of the status glyph, per step.
trace.renderMarker = ({ node, status }) =>
  status === 'warning' ? html`<c2-feather-alert-triangle></c2-feather-alert-triangle>` : node.icon

// A duration that ticks while the step is running.
trace.renderTrailing = ({ node, status }) => (status === 'running' ? elapsedSince(node.startedAt) : node.trailing)
```

`renderItem` takes over the row's **text** — it overrides `renderLabel`, `renderDetail` and `renderTrailing`. The
marker and the disclosure are their own columns rather than part of that text, so `renderMarker` and `renderToggle`
still apply alongside it:

```js tag=CodeBlock
trace.renderItem = ({ node }) => html`<a href=${node.href}>${node.label}</a> <c2-badge>${node.count}</c2-badge>`
trace.renderMarker = ({ node }) => node.icon
```
